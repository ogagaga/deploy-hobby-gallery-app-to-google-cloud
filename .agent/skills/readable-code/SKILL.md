# Readable Code Skill

このスキルは、コードを「理解しやすく」するための原則とガイドラインを提供します。
新しいコードを書く際や、リファクタリングを行う際に参照してください。

## 1. 基本原則 (Fundamental Principle)
> **コードは他の人が最短時間で理解できるように書かなければならない。**
("Code should be written to minimize the time it would take for someone else to understand it.")

## 2. 具体的なガイドライン

### 2.1 名前に情報を詰め込む (Packing Information into Names)
- **明確な単語を選ぶ**: `Get` ではなく `Fetch` や `Download` など、動作を具体的に表す単語を使う。
- **汎用的な名前を避ける**: `tmp`, `retval`, `data` などの曖昧な名前は避ける（どうしても必要な場合を除く）。
- **単位を含める**: 時間やサイズを表す変数には単位をつける (`delay_ms`, `size_mb`, `limit_kb`).
- **属性を含める**: 重要な属性であれば名前に含める (`plaintext_password`, `html_utf8`).

### 2.2 誤解されない名前 (Names That Can't Be Misconstrued)
- **限界値**: `min_`, `max_` を使う。
- **範囲**: `first_`, `last_` を使う（包含する場合）。
- **包含/排他**: `begin_`, `end_` を使う（endを含まない場合）。
- **ブール値**: `is_`, `has_`, `can_`, `should_` などで始め、肯定形にする（`disable_ssl = false` よりも `use_ssl = true` の方がわかりやすい）。

### 2.3 美しさ (Aesthetics)
- **一貫性**: 同じ概念には同じ変数名を使う。
- **整列**: コードの見た目を整え、読みやすくする（空行の使い方、インデント）。
- **宣言**: 変数は使用する場所の直前で宣言する。

### 2.4 コメントすべきこと (Knowing What to Comment)
- **「何」ではなく「なぜ」**: コード自体から明らかなことは書かない。コードの背後にある意図や理由を書く。
- **欠陥や未完成**: `TODO:`, `FIXME:`, `HACK:` などのタグを使う。
- **定数の理由**: なぜその値に設定したのかを説明する。
- **読み手の立場**: 読み手がどこで躓きそうかを予想してコメントする。

### 2.5 制御フローを読みやすくする (Making Control Flow Easy to Read)
- **条件式の並び順**: 左辺に「変化する値（調査対象）」、右辺に「比較対象（定数など）」を置く（`if (length >= 10)`）。
- **if/else ブロック**: 肯定形、単純な条件、目立つ条件を先に書く。
- **早期リターン**: ガード節を使って、ネストを浅くする。

### 2.6 巨大な式を分割する (Breaking Down Giant Expressions)
- **要約変数**: 複雑な式の一部を変数に代入して、意味のある名前をつける。
- **ド・モルガンの法則**: 論理式を簡略化する（`not (a or b)` は `not a and not b`）。

### 2.7 変数と読みやすさ (Variables and Readability)
- **変数を削除する**: 役に立たない一時変数は削除する。
- **スコープを縮める**: 変数の有効範囲（スコープ）をできるだけ小さくする。
- **書き込みを減らす**: 変数への再代入を減らし、できるだけ `const` (不変) にする。

## 3. レビュー時のチェックリスト

- [ ] その変数はもっと良い名前にできないか？
- [ ] そのコメントは本当に必要か？コード自体で語れるか？
- [ ] 条件分岐のネストは深くすぎないか？早期リターンできないか？
- [ ] 一つの関数が複数のことをしていないか？分割できるか？
- [ ] テストコードは読みやすいか？
